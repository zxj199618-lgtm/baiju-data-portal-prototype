# 业务线分组与业务线知识库设计

日期：2026-11-12

## 目标
- 表管理增加「业务线」一级分组（保险、存量、权益、AI 短剧……），每个业务线有自己的知识库，写业务背景、术语、指标口径、表地图、表间关联。
- AI 分析对话里用户选「业务线」而不是选表。业务线知识库进入系统上下文，模型据此判断需要哪些表、怎么关联，再按需取表知识库，最后取数回答。
- 表知识库保留，作用不变，但要落到服务端（现在只在页面内存里，网关读不到）。

成功标准：用户选一个业务线问一个跨表问题（例如"保险业务线上周各产品的消耗和订单"），模型能自己选出相关表、走登记过的关联取到平台算好的数字，且全程不越过该用户的表权限与字段权限。

## 已确认的决定
- 一张表只属于一个业务线；共享维表放进内置的「公共」业务线，所有业务线自动带上它。
- 表间关联用结构化清单维护，业务线正文另有 Markdown 知识库。
- 第一版就支持跨表取数（`query_join`），**不限制关联的表数量**；安全边界是"只能走登记过的关联"加资源上限。
- `@表` 与飞书机器人的老路径保留；业务线只对有权限的表可见；编辑权限跟「表管理」的编辑权限走。

## 现状（读代码得到）
- 表资产已有单值 `bizLine`（页面内存里的演示数据，值有 权益 / 存量 / 号卡 / 安全合规 等），工作台已按业务线给表分组并有"先问业务线"的澄清卡。
- 表知识库只在 `page-table-detail.js` 的 `tableKnowledgeStore`（内存，一张示例表）。
- 网关已是工具调用式取数（`search_tables` / `get_schema` / `query_metric` / `run_metric` / `attribute_change` / `get_lineage` / `get_sample_rows` / `ask_user`），**全是单表**。每次请求用 `scopeFor(user)` 生成字段权限视图，所有取数都走它。
- 网关已有 `businessLine` 请求参数，目前只用于缩小候选表范围。
- 服务端存储的既有模式：`org-store.cjs` 读写 `DATA_DIR/org.json`，`GET/PUT /v1/org`，管理员保存、写审计。

## 1. 数据与存储
新增 `scripts/knowledge-store.cjs`，文件 `DATA_DIR/knowledge.json`，写法参照 `org-store.cjs`（校验、限长、保存时写审计）。

```json
{
  "businessLines": [
    { "id": "BL01", "name": "保险", "order": 10,
      "knowledge": { "markdown": "...", "updatedBy": "曾祥竞", "updatedAt": "2026-11-12 10:00" },
      "relations": [
        { "id": "R001", "left": { "table": "用户订单明细", "field": "user_id" },
          "right": { "table": "用户画像标签明细表", "field": "user_id" },
          "type": "N:1", "note": "订单按用户取标签" }
      ] }
  ],
  "tableLines": { "用户订单明细": "保险", "渠道维表": "公共" },
  "tableKnowledge": { "广告计划日报表": { "markdown": "...", "updatedBy": "...", "updatedAt": "..." } }
}
```

- 内置业务线「公共」：不可删除、不可改名、不能作为对话入口；它的知识库与关联清单并入每个业务线的上下文。
- 一张表在 `tableLines` 里最多一个值；没有记录的表视为「未分组」，只能通过 `@表` 使用。
- 关系类型取 `1:1` / `1:N` / `N:1`，用于重复计数判断（见第 3 节）。字段必须存在于网关真实表定义；表必须存在。
- 同一对表可登记多条关联（不同字段对），`id` 全局唯一。
- 业务线改名：服务端同步改 `tableLines` 的值；有表的业务线不允许删除（返回需先迁出的表名）。
- 限长：业务线知识库 ≤ 20000 字、表知识库 ≤ 10000 字、每个业务线关联 ≤ 200 条、业务线数量 ≤ 50。
- 首次启动种子：从现有 `bizLine` 演示值生成业务线（权益、存量、号卡……）与 `tableLines`，把「广告计划日报表」的示例表知识库导入；保险、AI 短剧等由管理员在界面里新增。
- **页面数据来源**：服务端是唯一来源。页面登录后读取，保存时写回；页面内存里的 `bizLine` 改为读取 `tableLines` 的结果。

接口（均在登录之后）：

| 方法与路径 | 说明 | 权限 |
|---|---|---|
| `GET /v1/knowledge` | 业务线列表（含知识库、关联）、`tableLines`；非管理员只返回自己有权限的表所在的业务线，且关联按字段权限过滤 | 登录用户 |
| `PUT /v1/knowledge/business-lines` | 保存业务线列表（含知识库与关联）与 `tableLines` | 有「表管理」编辑权限 |
| `GET /v1/knowledge/tables/:表名` | 读一张表的知识库（需有表权限，正文按隐藏字段逐行脱敏） | 登录用户 |
| `PUT /v1/knowledge/tables/:表名` | 保存表知识库 | 有「表管理」编辑权限 |

写入全部记审计（`knowledge-change`，含业务线 / 表名与操作人，不记正文）。

## 2. 表管理页
- 表管理顶部增加「数据表｜业务线」两个视图。数据表视图原有的业务线筛选与新增表时的业务线选择，改为从服务端业务线列表取值（含「公共」）。
- 业务线视图：左侧业务线列表（名称、表数），支持新增 / 改名 / 排序；右侧三个子页：
  - **知识库**：Markdown 编辑与预览，复用现有编辑器与「规范成 Markdown」逻辑。新建模板：业务概述、术语与口径、核心指标、表地图（每张表一句话说什么时候用）、常见分析套路、注意事项。
  - **表关联**：清单表格，增删改；左右表与字段用下拉选（字段取自真实表结构），选关系类型、写备注；保存时校验两端存在。
  - **包含的表**：该业务线下的表，可把表移入 / 移出（改 `tableLines`）。
- 把 `page-table-detail.js` 里的 Markdown 渲染、规范化、编辑工具抽成共用文件（新增 `assets/portal/knowledge-md.js`，进 `manifest.json` 与 `index.html`，版本号同步），表详情页与业务线页共用，表详情页的知识库改读写服务端接口。

## 3. AI 对话流程
前端：输入框下方"选择数据表"级联改为"选择业务线"单选，只列出该用户在其下（或「公共」下）至少有一张有权限的表的业务线。请求带 `businessLine`；`@表` 仍可用，两者同时给时以 `@表` 为主、业务线上下文作为背景。

网关收到 `businessLine` 后：
1. 取用户有权限的表：`tableLines` 为该业务线或「公共」的表，与表权限求交，再套 `scopeFor(user)` 字段权限视图。
2. 生成**业务线上下文包**放入系统上下文：业务线知识库、「公共」知识库（均按隐藏字段逐行脱敏）、可用表清单（表名、一句话说明、有无表知识库）、过滤后的关联清单。
3. 工具（业务线模式下额外提供）：
   - `get_table_knowledge`：入参表名数组，返回表知识库。不限制表数，按**总字数预算**（默认 30000 字符，可配置）按模型点名顺序截断并注明哪些没给；无权限与不存在的表提示一致。
   - `query_join`：模型声明表、指标、分组维度、筛选、窗口天数，**不写关联条件**。网关在该业务线（含「公共」）的关联图里找连通路径，中间可经过没被点名的表，不限跳数与表数。
     - 找不到路径：明确返回"X 与 Y 在关联清单里没有登记"，由模型 `ask_user` 或如实说明，不猜关联键。
     - 重复计数防护：沿用"先分别汇总再相除"。关联前把各表先汇总到连接键粒度再拼；指标来自一对多关系"1"的一侧、却要按"N"的一侧分组或筛选时，拒绝执行并说明原因，不静默给错数字。
     - 资源上限：关联中间结果行数、总耗时、返回大小（均可配置），超限返回明确错误。
     - 每次调用校验表权限与字段权限；任一端表或字段被隐藏，整条关联视为不存在；写审计。
   - 原有单表工具照常可用。
4. 系统提示追加顺序要求：先按问题判断需要哪些表，再 `get_table_knowledge` 与 `get_schema`，再取数；跨表用 `query_join`；数字只引用工具返回值。
5. 工具调用上限在业务线模式下放宽到默认 8 轮 / 20 次，做成可配置，评测后再调。

没选业务线、飞书机器人入口：保持现有流程，不受影响。

## 4. 权限、边界与错误处理
- 表权限、字段权限一律以服务端为准；业务线只是在其之上缩小范围，不授予任何权限。
- 知识库 Markdown 里提到被隐藏字段的行，在给模型与返回给页面时按 `field-scope.cjs` 的 `redactLines` 整行替换为「（已隐藏）」（和 Skill 规范包同一套规则）。已知边界：别名与中文叙述写法不处理。
- 关联清单里引用的表被删除或字段不存在：保存时校验拒绝；已存在的失效关联在读取时标记失效并忽略，页面提示管理员。
- `knowledge.json` 损坏或缺失：按空数据启动并在日志告警，不阻塞网关。
- 业务线下没有可用数据：沿用现有 404 提示。

## 5. 测试
- 单元：`knowledge-store`（校验、限长、改名同步、删除保护、种子）；关联图路径查找（多跳、无路径、环）；重复计数判定；字段权限下关联过滤与知识库脱敏。
- 网关端到端：业务线模式下的上下文包内容、`get_table_knowledge` 预算截断、`query_join` 跨三张以上表取数与拒绝场景、无权限与隐藏字段不泄露。
- 浏览器端到端：表管理业务线视图增改、工作台选业务线发问、旧路径（`@表`）不回归。
- 评测：往 `evals/cases.json` 加跨表问题（多表关联、无关联登记、一对多重复计数陷阱）。
- 路由：业务线视图是否需要独立地址（`portal-routes.js`）在计划阶段确认，默认加 `#/asset/business-lines`。
