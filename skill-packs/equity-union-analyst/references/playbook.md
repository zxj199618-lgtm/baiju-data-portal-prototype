# 分析指引

本文件把常见的业务提问映射到分析框架。每一节给出：适用问法 → 口径要点 → 分析步骤 → 输出结构 → 易错点。

**所有分析开始前，先跑 §1 的数据探查。** 这不是可选项——本表是异步物化视图，数据可能滞后，且某些账号/部门根本没有数据，直接取数会得出「消耗为 0」这类误导结论。

## §1　数据可用性探查（前置）

目标：确认「有数据」和「数据新鲜」。

探查三件事：

1. **有没有数据**：目标日期范围的行数、消耗合计、`mv_update_time` 最大值
2. **集群里实际有哪些 `department`**：不要假设 `'达人部门-权益'` 一定存在，值可能带空格或变体
3. **`commodity_classify` 的实际写法**：确认 `常规套餐` 与 `三方支付套餐` 这两个值的准确拼写（防空格/别名导致漏数）。若查出其他取值，不纳入分析，也不必在结论中提及

输出给用户的形式：

> 数据截至 {mv_update_time}，{日期} 覆盖 {M} 个账号、{D} 个部门。常规套餐（自营）消耗占比 {x}%、三方支付套餐（CPA）{y}%。

若行数为 0，**不要直接回答「消耗为 0」**，要区分两种可能：真没投放，或视图未刷新。此时查 `mv_update_time` 与 `current_date()` 的差距。

## §2　单点总量类

**典型问法**：「今天消耗多少」「任哥昨天花了多少钱」「存量昨天花了多少」「三方今天多少单」

口径要点：

- 「今天」= `head_data_date = current_date()`
- 「任哥」→ `department IN ('投放一部-权益一组','投放一部-权益二组')`
- 「存量 / 子墨」→ `account_id = '白驹存量'`（账号口径，不是部门口径）
- 「白驹」→ **歧义，先反问是部门还是 `白驹存量` 账号**，见 `SKILL.md` 硬口径③
- 只取 `常规套餐`（自营）与 `三方支付套餐`（三方/CPA）两类，其余取值不过滤进任何统计
- 「总消耗」用两类合计；「转化/签约」只用 `常规套餐`；「CPA 效果」只用 `三方支付套餐`
- 消耗看 `cash_cost`，别默认用 `book_cost`

输出结构：一句话结论 + 3–5 个核心数字（消耗、成功用户数、成功订单数、收入、每成功用户成本），每个数字附上口径。

易错点：只报 `cash_cost` 不报口径，用户无法判断这是含无订单消耗的全量口径。

## §3　趋势分析

**典型问法**：「近 7 天消耗趋势」「这周比上周怎么样」

口径要点：

- 按 `head_data_date` 分组。**订单与消耗不同轴，日级转化率会跳动**，趋势图上要说明
- 跨 2026-09-21 的区间必须标注 `success_*_2h` 口径断点
- 用户级指标日汇总后 `SUM` 会重复，趋势用「日用户人次」表述

分析步骤：

1. 按日聚合消耗、成功用户、收入
2. 计算日均、最高/最低日、波动系数（标准差/均值）
3. 标记异常日（偏离均值超过 2 倍标准差的点）
4. 对每个异常日下钻到 §4 或 §8 定位原因

输出结构：迷你表格（日期 × 消耗 × 用户 × 成本）+ 一句话趋势判断 + 异常日清单。

易错点：把「订单数在首单日、消耗在消耗日」导致的日级 ROI 抖动当成业务异常。

## §4　结构占比分析

**典型问法**：「消耗都花在哪些账号」「部门消耗占比」「套餐结构」

口径要点：

- 占比的分子分母必须同口径同范围
- 用消耗占比时按 `cash_cost`，用收入占比时自营按 `pay_amount`、三方按 `report_reward`，**不能混**
- 账号数多时取 Top 10 + 其他合计，不要铺满表格

输出结构：Top N 表格（名称 / 消耗 / 占比 / 累计占比）+ 集中度判断（前 3 名占比是否超过 70%）。

业务解读要点：

- 消耗集中在少数账号 → 风险集中，单账号停投影响大
- 消耗分散但成功率差异大 → 存在结构性优化空间
- 某套餐消耗占比高但净留存率低 → 可能是拉新型套餐，需结合回本看

## §5　横向对比与排名

**典型问法**：「哪个账号效率最高」「优化师排名」「哪个套餐最能跑」

口径要点：

- **排名必须用效率指标，不能用绝对量**。账号 A 花 10 万获得 100 个用户，账号 B 花 1 万获得 50 个用户，A 的消耗高但效率低
- 效率指标优先用「每成功用户现金消耗」，其次「提单签约率」
- 分母太小的样本要过滤（如 `success_user_cnt < 5` 的不参与排名），否则 1/1=100% 会排第一

分析步骤：

1. 按目标维度聚合（账号 / 优化师 / 套餐 / 部门）
2. 计算消耗、成功用户、单用户成本、签约率
3. 过滤小样本
4. 按效率排序，同时给出效率与规模两个维度

输出结构：对照表 + 「高效率高规模 / 高效率小规模 / 低效率大消耗」四象限归类。

易错点：对率求平均排名（见 metrics §4.4）。

## §6　漏斗诊断

**典型问法**：「转化哪里出问题了」「为什么签不下来」

漏斗链路（仅自营 `常规套餐`）：

```
曝光 view_count
  ↓ CTR
点击 click_count
  ↓ 平台回传
转化 conversion_count
  ↓（平台口径与站内口径不同，仅作参考）
有效提单 valid_user_cnt
  ↓ 提单签约率
签约 contract_user_cnt
  ↓ 签约成功率
支付成功 success_user_cnt
  ↓ 净留存率
有效用户 valid_success_user_cnt
```

口径要点：

- 前三级（曝光→点击→转化）是**平台侧**指标，来自 ct 路，按消耗日
- 后三级（提单→签约→成功）是**站内**指标，来自 od 路，按首单日
- **两段不同轴，不能把整条链路当成一天内的漏斗**。分析时要说明「前端效率」和「后端转化」分属不同时间窗口
- 三方套餐不适用签约段

分析步骤：

1. 算出各层级转化率
2. 与自身历史或同部门其他账号对比
3. 找出跌幅最大的那一级
4. 定位到具体账号/套餐

输出结构：漏斗表（层级 / 数量 / 转化率 / 环比）+ 瓶颈定位 + 待验证假设。

**归因方向参考**（仅作假设，不要当结论）：

| 瓶颈位置 | 可能方向 |
|---|---|
| 曝光→点击 低 | 素材/定向问题 |
| 点击→转化 低 | 落地页/承接问题 |
| 提单→签约 低 | 签约流程阻力、套餐吸引力、价格 |
| 签约→支付 低 | 扣费通道、扣费失败，查 `faild_pay_user_cnt` |
| 成功→留存 低 | 解约/退款，查 `off_contract_user_cnt`、`refund_user_cnt` |

## §7　自营 vs 三方对比

**典型问法**：「自营和三方哪个划算」「CPA 跑得怎么样」

口径要点（这是最容易被算错的一组）：

| | 自营（`常规套餐`） | 三方（`三方支付套餐`） |
|---|---|---|
| 收入口径 | `pay_amount` / `real_pay_amount` | `report_reward` |
| 核心转化 | 签约漏斗 | 支付成功 |
| 成本效率 | 每成功用户现金消耗 | 每成功用户现金消耗 |
| ROI | `pay_amount / cash_cost` | `report_reward / cash_cost` |
| 不适用 | — | `contract_*` 系列 |

分析步骤：

1. 分别聚合两类套餐的消耗、成功用户、收入
2. **各自算 ROI，不做合并 ROI**（分子口径不同）
3. 对比效率：哪类每成功用户成本更低
4. 对比规模：哪类贡献更多消耗/收入

输出结构：两列对照表 + 结论「单位成本」与「规模贡献」分开说。

易错点：把 `report_reward` 加进自营收入，或把 `pay_amount` 当三方收入——两者都会得出完全错误的 ROI。

## §8　环比异常归因

**典型问法**：「昨天消耗怎么掉了」「这周比上周差在哪」

分析步骤（维度逐层下钻）：

1. **确认是真跌还是口径问题**：先看行数变化、`mv_update_time`、是否有账号停止投放
2. **按部门切**：是全部门普跌，还是某个部门拖累
3. **按账号切**：定位到具体账号
4. **按套餐切**：是套餐停投还是转化变差
5. **区分量价**：消耗跌是因为曝光少了（量），还是 CPM 涨了（价）；成功用户跌是因为提单少了，还是签约率降了
6. **检查口径断点**：区间是否跨 2026-09-21

输出结构：

> 昨日消耗 {A}，环比 {±x}%（{绝对差额}）。其中 {部门X} 贡献 {y} 个百分点的降幅，主因是 {账号Y} 停投（该账号前日消耗 {z}）。其余部门环比波动在 ±{w}% 内，属正常。

易错点：只看总量不看结构，把「单账号停投」说成「整体效率下滑」。

## §9　小时级与实时监控

**典型问法**：「今天几点消耗最快」「现在跑到多少了」

口径要点：

- `head_data_hour` 在订单侧是**首单小时**、消耗侧是**消耗小时**，两者错位
- **小时级只能看消耗与流量，不能看转化**。若用户要小时级转化，必须说明本表不支持
- 实时性受物化视图刷新控制，最新小时可能不完整

输出结构：小时曲线（0–23）+ 累计消耗 + 当前时点消耗进度（对比昨日同时段）。

## §10　收入与回本

**典型问法**：「这个月回本了吗」「ROI 多少」

口径要点：

- 自营：`pay_amount / cash_cost`（毛）或 `real_pay_amount / cash_cost`（净）
- 三方：`report_reward / cash_cost`
- **必须声明区间**：日级 ROI 不可信（订单与消耗不同轴），至少周/月口径
- 跨期首单会低估 ROI：窗口开始前发生的首单，其续费消耗落在窗口内，但订单数已计入上个窗口

分析步骤：

1. 选定周期（周/月），按部门或账号聚合
2. 计算收入、消耗、ROI
3. 对比目标 ROI（若用户未给目标，不给「是否达标」结论）
4. 若 ROI < 1，拆解是成本高还是转化差

输出结构：ROI 表 + 归因（成本侧 / 转化侧 / 客单价侧）。

## §11　输出模板

任何分析结论建议按此结构组织：

```
【结论】一句话回答用户的问题，带核心数字。

【明细】
| 维度 | 消耗 | 成功用户 | 每用户成本 | 收入 | ROI |
|---|---|---|---|---|---|

【口径】
时间：2026-10-21（数据截至 18:30）
范围：department IN ('投放一部-权益一组','投放一部-权益二组')（任哥）
套餐：常规套餐（自营）
说明：用户数按账号内去重，跨账号累加存在重复

【边界】
- 日级 ROI 受订单/消耗不同轴影响，建议看周口径
- 该区间不跨 2026-09-21，success_*_2h 口径一致
```

## §12　追问策略

用户提问模糊时，一次问清**最多两个**最关键的问题，其余给默认值并在结论中声明。优先级：

1. 时间范围不明确 → 默认今天，同时给近 7 天趋势（覆盖度更高）
2. 对象不明确（「帮我看看效果」）→ 默认全部门 + 按部门拆分，让用户自己定位
3. 指标不明确 → 默认「消耗 + 成功用户 + 每用户成本 + 收入」四件套

不要连续追问三轮，第二轮回合必须给出带默认假设的结果。

**唯一的必问项是「白驹」**——它既可能指部门（投放一部，任哥）、也可能指账号（`白驹存量`，即存量/子墨），两者范围完全不同，不能给默认值。处理方式：反问一句，同时**并列算出两种口径的数**放进同一个回答，用户看到数字就能自己判断指的是哪个。「存量」「子墨」无歧义，不需要问。

## §13　无法回答的情况

| 需求 | 原因 | 建议 |
|---|---|---|
| 按商户号/支付渠道拆分 | 三列恒 NULL | 换 `dwd_equity_shop_profit_detail_f_d` |
| 精确全局去重用户数 | 用户指标不可加 | 回明细表 `COUNT(DISTINCT phone)` |
| 单个订单明细追溯 | 本表已按 21 维度聚合 | 回明细表 |
| 小时级转化率 | 两侧时间轴错位 | 只用日级 |
| 有效订单消耗（剔除无订单消耗） | 本表已合并 `no_order_cash_cost` | 回明细表 |
| 用户生命周期/LTV | 本表无用户级明细与长周期 | 需其他表 |
